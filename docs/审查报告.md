## 第 1 轮 · 首版实现

> 流程：四视角并行审查 → 主智能体回读源码核实 → 问题当场修复并复测
> 日期：2026-10-23 · 需求：实时显示 2.4G 设备电量、显示在时间栏旁、支持开机自启

### 一、本轮改动

新增单文件 WinForms 托盘程序 `BatteryTray.exe`（.NET Framework 4.x，系统 csc 编译），包含：

- `src/LogitechBatteryReader.cs`：枚举 HID 接口，通过罗技 HID++ 2.0 长报文通道读取配对设备电量（特性 `0x1000` / `0x1004`）；SONiX 接收器标记为不支持。
- `src/ClockBarForm.cs`：任务栏时钟左侧的悬浮文字条，鼠标穿透、置顶、跟随主题与 DPI。
- `src/Program.cs`：托盘图标（百分比）、右键菜单、10 秒轮询、快照合并与上次值缓存、注册表开机自启、单实例。
- `src/Native.cs`：SetupAPI / HID / user32 / kernel32 互操作声明。

### 二、审查发现与处置

| # | 视角 | 问题 | 处置 |
|---|------|------|------|
| 1 | 线程与资源 | P0：overlapped `WriteFile` / `ReadFile` 直接传 `byte[]`，`ERROR_IO_PENDING` 后托管数组可能被 GC 移动；取消后仅等待 150ms 就关闭事件 | ✅ 改为 `GCHandle` 固定请求缓冲区、`Marshal.AllocHGlobal` 承载读缓冲；取消后 `GetOverlappedResult(..., true)` 等待完成再释放 |
| 2 | 正确性 | P1：HID++ 错误帧只按 `[2]==0x8F` 判断；响应未校验报告 ID / swId；电量读取的错误帧可能被当成百分比 | ✅ 同时识别 `[2]==0xFF && [3]==0x8F` 与 `0x8F`；匹配增加报告 ID、设备索引、swId；电量响应先判错再解析 |
| 3 | 线程与资源 | P1：在“退出”菜单 Click 内同步释放菜单，存在重入/`ObjectDisposedException` 风险 | ✅ 退出延后到 `SynchronizationContext.Post`；释放前清空 `ContextMenuStrip` |
| 4 | 正确性 | P2：`0x1004` 的 0% 被当成未知；`0x1000` 的 0 才表示未知 | ✅ 按特性区分；UI 以 `-1` 表示未知、`0` 表示 0% |
| 5 | 交互 | P2：每次启动无条件写 Run 键，会恢复用户已外部禁用的自启 | ✅ 菜单勾选以 Run 键实际状态为准；仅首次运行默认开启；外部禁用不再被覆盖（已实测） |
| 6 | 正确性 | P2：接收器拔掉后旧快照永不替换，可能长期显示旧电量 | ✅ 快照中确认“未检测到接收器”时立即换入；设备休眠仍保留上次值（有意设计） |
| 7 | 交互 | P2：`NotifyIcon.Text` 不支持换行，且 63 字符硬截断可能丢失重点 | ✅ 改为单行 `·` 分隔，超长时保留 60 字符并加省略号 |
| 8 | 交互 | P2：托盘图标按 stale 变灰的分支实际不可达 | ✅ 移除 stale 参数；仅未知显示灰色问号，0% 正常显示红色 |
| 9 | 交互 | P2：文字条先 Show 再定位，且取不到时钟时每 2 秒 Show/Hide 抖动 | ✅ 先取时钟矩形，再设置 `Bounds` 后显示；无有效位置直接隐藏 |
| 10 | 架构 | P3：未使用的 P/Invoke、`using`、`Usage` / `Updated` 字段、无效句柄创建语句 | ✅ 已清理 |
| 11 | 线程与资源 | P3：`Icon.FromHandle` + `Clone` + `DestroyIcon` 的所有权存疑 | ⚠️ 核实为误报：`Clone()` 生成独立句柄图标，`DestroyIcon` 只销毁临时 HICON，顺序正确 |

### 三、误报澄清

- **托盘图标句柄**：智能体担心 `Icon.FromHandle` 克隆后立即 `DestroyIcon` 会得到空图标。已核实 `Icon.Clone()` 会复制图标数据并持有独立句柄，原 HICON 仅用于克隆，销毁是正确做法；离屏渲染与托盘显示均正常。
- **HID 句柄泄漏**：逐条回读 `EnumerateHidInterfaces`、`GetCaps`、`HidConnection.Open/Dispose`，SetupAPI 列表、preparsed data、CreateFile 句柄均在 `finally` 或 `using` 中释放，未发现泄漏。
- **轮询并发**：`Interlocked.Exchange` 守卫有效；`_Stale` 仅在 UI 线程修改，后台线程只读新建快照，未发现数据竞争。

### 四、测试

- 编译：系统 `csc.exe`（.NET Framework 4.0.30319）编译通过，0 错误。
- 真机读取：罗技接收器 `VID_046D PID_C534`，设备索引 1，特性 `0x1000` 返回 30%（下一档 5%）；SONiX `VID_26CE PID_01A2` 无标准电量特性，状态窗口显示“不支持”。
- UI：DPI 感知截图确认时钟左侧显示“2.4G 30%”，文字完整；托盘图标 32×32 渲染为橙色“30”。
- 缓存与更新：写入 55% 缓存后启动，界面先显示 55%，15 秒内被真实读数 30% 覆盖，`LastPercent` 同步更新为 30。
- 自启：外部删除 Run 键后启动不会自动恢复；删除 `AutoStart` 设置模拟首次运行后，自动写入当前 exe 路径。
- 未覆盖：真实重启后的自启、长时间休眠唤醒、拔插接收器、副屏/竖向任务栏、托盘图标被系统折叠到溢出区的场景。

### 五、遗留

- P2：按 `VID:PID` 分组接收器，两个同型号接收器会被合并；当前机器只有一台，未改。
- P2：读取层内含中文界面文案（厂商分支、状态细节），后续增加其他厂商时建议上移到 UI 层。
- P2：文字条覆盖通知区“隐藏图标”箭头；已设置鼠标穿透（箭头仍可点击）并提供“显示在时间栏旁”开关，属于用户选择的布局取舍。
- P2：设备休眠时保留上次电量；状态窗口显示最近成功读取时间，不自动过期。
- P3：托盘图标固定 32px，高 DPI 下数字偏小；时钟旁文字条提供清晰读数。
- P3：仅定位主任务栏 `Shell_TrayWnd`，副屏与竖向任务栏不显示文字条。
- P3：按需求不做低电量弹窗提醒。
- P3：最坏情况下 6 个设备索引全部超时会超过 10 秒，`_polling` 守卫会丢弃重叠的 tick，不会并发读写。

### 六、结论

- 本轮修复 9 项（含 P0 1 项、P1 2 项、P2 5 项、P3 1 项），保留 7 项已知限制。
- 无未处理的 P0/P1；真机读数、时钟旁显示、缓存更新、自启开关均已复测。
- 可以试用发布；按用户要求**未执行任何 git 提交**。

## 第 2 轮 · 四类设备面板与多品牌重构

> 流程：四视角并行审查 → 主智能体回读源码核实 → 问题当场修复并复测
> 日期：2026-10-23 · 需求：面板置于时钟上方，显示手柄/鼠标/键盘/耳机四类设备，淡色图标、无数字、电池图形，兼容 2.4G/蓝牙/USB 有线

### 一、本轮改动

- UI：删除时钟左侧文字条，改为 220×48 的四槽面板，位于时钟正上方、右对齐；每槽为淡色类别图标 + 电池图形；无设备时图标淡化、电量未知用虚线轮廓、0% 用红色底线；蓝牙未知显示蓝牙符号、USB 有线显示插头；面板整体 0.88 不透明度，跟随深浅主题。
- 托盘：图标改为淡色电池轮廓，不显示数字；工具提示与状态窗口保留分类百分比用于诊断。
- 数据模型：新增 `DeviceCategory`（手柄/鼠标/键盘/耳机/其他）与 `DeviceConnection`（2.4G/蓝牙/USB 有线/未知）。
- 多品牌读取框架：`IBatteryProvider`，顺序为 Logitech HID++ 2.0 → 标准 HID 电池字段（Usage 0x06/0x20）→ HID 设备分类/连接识别 → 蓝牙设备识别（WMI）→ XInput 手柄识别。
- 快照合并：按类别/接收器保留上次成功电量，接收器消失时清除；缓存 `LastCategory` + `LastPercent`，设备休眠时仍能显示上次分类电量。
- 蓝牙：通过 WMI 列出在线蓝牙设备（QCY-T13 识别为耳机），但当前 csc/.NET Framework 工具链无法调用 BLE GATT（缺少 WinRT 统一元数据），电量标注为未知，不伪造读数。
- 私有协议：未做自动逆向；未知品牌按厂商/产品名标注，`IBatteryProvider` 作为后续品牌适配的扩展点。

### 二、审查发现与处置

| # | 视角 | 问题 | 处置 |
|---|------|------|------|
| 1 | 正确性 | P1：任一设备读取成功就整体替换快照，其他休眠类别丢失上次电量 | ✅ `MergeSnapshots` 按接收器前缀/类别逐项合并，保留上次值并标记 Stale；接收器消失则清除 |
| 2 | 正确性 | P1：0x1004 统一电池误把功能 0（能力）当电量；正确状态是功能 1 | ✅ 先读能力功能 0，检查 state-of-charge 标志位（[5] & 0x02），再读功能 1；依据 Linux hid-logitech-hidpp 补丁核对 |
| 3 | 正确性 | P1：仅凭 VID 046D/26CE 判定 2.4G，有线罗技/26CE 设备被误标 | ✅ 仅当同组存在 `UsagePage 0xFF00` 厂商集合时判 2.4G，否则 USB 有线/蓝牙 |
| 4 | 正确性 | P1：接收器拔掉但仍有其他 HID 时，旧电量永久显示 | ✅ 合并时检查旧键前缀是否仍存在于新快照，不存在则丢弃 |
| 5 | 正确性 | P1：“LED Controller” 被关键词 “controller” 误判为手柄 | ✅ 手柄关键词收窄为 gamepad/game controller/joystick/手柄等；不再匹配 LED Controller |
| 6 | 架构 | P2：标准 HID 读取器跳过全部罗技设备，罗技蓝牙/有线无法使用标准电量 | ✅ 仅跳过含 0xFF00 的罗技 HID++ 接收器组，其他罗技接口继续尝试标准 HID 电池 |
| 7 | 正确性 | P2：WMI 未过滤离线蓝牙设备，可能长期显示幽灵耳机 | ✅ 查询增加 `ConfigManagerErrorCode=0`；文案改为“已识别”而非“已连接” |
| 8 | 交互 | P1：0% 与电量未知都显示空电池，无法区分 | ✅ 0% 画红色短线并保持实线轮廓；未知使用虚线轮廓 |
| 9 | 交互 | P1：陈旧缓存值与实时值外观一致 | ✅ Stale 图标透明度降低、填充透明度降低；工具提示/状态窗口标注“上次读取” |
| 10 | 交互 | P2：位置未变时不再 SetWindowPos，可能被其他置顶窗口压住 | ✅ 每 2 秒重申 TopMost；已复测面板可见 |
| 11 | 线程 | P2：面板禁用后 2 秒定时器仍反复 Hide | ✅ 禁用时停止定时器，启用时恢复 |
| 12 | 线程 | P2：overlapped I/O 的 `lpNumberOfBytesRead/Written` 应传 NULL | ✅ P/Invoke 改为 `IntPtr.Zero`，字节数统一由 `GetOverlappedResult` 取得；复测仍读到 30% |
| 13 | 线程 | P2：WMI 的 `ManagementObjectCollection`/`ManagementObject` 未释放 | ✅ 使用 `using` 释放集合与对象 |
| 14 | 交互 | P2：蓝牙图形绘制超出 48px 面板高度 | ✅ 上移 4px，避免裁切 |
| 15 | 交互 | P2：面板无无障碍名 | ✅ 增加 `AccessibleName = "设备电量面板"` |
| 16 | 架构 | P3：`ShortLabel`、`Primary` 无引用；四类数组重复 | ⚠️ 保留 `ShortLabel` 作为后续文案扩展；`Primary` 仍被聚合层使用，暂不删除 |

### 三、误报澄清

- **0x1004 功能号**：智能体报告“get_status 是功能 1”经查证属实，已按 Linux `hid-logitech-hidpp` 补丁（`CMD_UNIFIED_BATTERY_GET_CAPABILITIES 0x00`、`CMD_UNIFIED_BATTERY_GET_STATUS 0x10`）修复，不是误报。
- **overlapped 缓冲区/取消等待**：上一轮已用 `GCHandle` + `AllocHGlobal` + `CancelAndWait` 修复；本轮复核仍成立，未回退。
- **同一型号双接收器合并**：确为 `VID:PID` 分组的已知限制；本轮未改（当前机器只有一只罗技接收器），记录在遗留。
- **面板被任务栏/开始菜单遮挡**：截图验证时开始菜单曾覆盖面板；关闭后面板正常显示。面板本身为 TopMost，每 2 秒重申。

### 四、测试

- 编译：系统 csc（.NET Framework 4.0.30319）+ `System.Management.dll`，0 错误。
- 真机：罗技 C534 接收器设备 1，HID++ 0x1000 读到 30%，DeviceType 识别为键盘；接收器同时识别出鼠标类别；QCY-T13 识别为蓝牙耳机且电量未知；SONiX LED Controller 不再误判为手柄。
- 休眠：设备休眠时 `ReadAll` 约 4.8–5.1 秒返回无电量；面板保留上次键盘 30%（Stale 淡化），鼠标/耳机类别仍显示。
- 唤醒：发送 Shift 后重新读取，2.9 秒内读到键盘 30%，确认 overlapped P/Invoke 修改未破坏读取。
- UI：截图确认四槽面板在时钟正上方，深色半透明背景、淡色图标、无数字；托盘为淡色电池轮廓。
- 构建依赖：`System.Management.dll`（.NET Framework 自带）；XInput 使用 `xinput1_4.dll`（Windows 8+）。

### 五、遗留

- P1：蓝牙耳机/鼠标的电量需要 BLE GATT（0x180F/0x2A19）；当前工具链缺少 WinRT 统一元数据，无法读取。已在状态窗口明确标注，不伪造。
- P1：私有 2.4G 协议（雷蛇、赛睿、海盗船、部分国产芯片等）未做自动逆向；`IBatteryProvider` 提供扩展点，但每个品牌仍需协议与实测。
- P1：同型号双接收器按 `VID:PID` 合并；当前单接收器场景无影响。
- P2：`CancelIo` 后等待完成无硬超时，极端驱动卡死时轮询线程可能挂起。
- P2：最坏情况（设备休眠 + 多个索引超时）单轮约 5 秒，低于 10 秒；若驱动异常可能超过 10 秒，`_polling` 守卫会丢弃重叠 tick。
- P2：面板仅跟随主任务栏 `Shell_TrayWnd`；副屏任务栏、竖向任务栏不显示面板。
- P3：蓝牙/耳机无法读电量时仅显示蓝牙符号，槽位信息量有限；Slot 无读屏文字。

### 六、结论

- 本轮修复 15 项（P1 8 项、P2 6 项、P3 1 项），保留 7 项已知限制。
- 四类面板、时钟上方定位、淡色无数字、2.4G/蓝牙/USB 分类、键盘 30% 真机读数均已复测。
- 私有协议与 BLE GATT 电量属于外部能力限制，已在 UI 与文档中如实说明。
- 可以试用；按用户要求完成本地仓库提交，未配置远程、未推送。

## 第 3 轮 · 刷新/鼠标/蓝牙定向修复

> 流程：主智能体回读源码 + 真机探测 + 定向验证（非完整四视角评审）
> 日期：2026-10-23 · 反馈：刷新太慢、拔掉设备不消失、接收器上的鼠标没有电量、蓝牙电量不显示

### 一、本轮改动

- 刷新：轮询从 10 秒改为 2 秒；新增 `DeviceChangeWindow`（`NativeWindow` + `WM_DEVICECHANGE`）在 USB/蓝牙设备插拔时立即触发刷新；轮询中收到事件会记录 pending，当前读取结束后立即补一次。
- 快照合并：保留上次电量时同时要求“同类别仍存在”；接收器/类别消失立即清除旧值，避免拔掉设备后永久显示。
- 鼠标：HID++ 2.0 探测确认设备 2 为 `Wireless Mouse`（DeviceType=3），特性表无 0x1000/0x1001/0x1004；HID++ 1.0 寄存器 0x07/0x0D（含先读 0x00、置 bit4 开启上报）均返回错误 0x01。结论为该鼠标不向系统/接收器提供电量，面板保留鼠标图标并显示虚线空电池，状态窗口写明原因。
- 蓝牙：新增 `BleGattBatteryProvider`，用 WinRT `Windows.Devices.Bluetooth` 在后台扫描所有 GATT 服务中的 `0x2A19` Battery Level 特征；结果缓存 30 秒，避免阻塞 2 秒轮询。按 BLE 设备名匹配现有蓝牙耳机条目，成功则更新电量。
- 构建：引入 `lib/winrt/` 下的 `Windows.WinMD`、`Windows.Foundation.UniversalApiContract.winmd`、`Windows.Foundation.FoundationContract.winmd`，并引用 .NET Framework 的 `System.Runtime`/`System.Runtime.WindowsRuntime` 程序集。
- 文案：罗技鼠标无电量时明确标注“该鼠标未提供电量上报（HID++ 2.0 特性表与 1.0 寄存器均不可用）”；蓝牙设备标注“未找到标准 GATT 电量服务”。

### 二、验证与处置

| # | 问题 | 处置与验证 |
|---|------|-----------|
| 1 | 拔插设备 10 秒内不刷新 | ✅ 2 秒轮询 + WM_DEVICECHANGE；补 pending 刷新 |
| 2 | 接收器/设备消失后旧电量残留 | ✅ `MergeSnapshots` 要求同类别仍存在，否则清除 |
| 3 | 鼠标无电量 | ✅ 实测设备 2 名称/类型与特性表；确认无 HID++ 2.0/1.0 电量通道；状态窗口说明 |
| 4 | 蓝牙电量不显示 | ✅ 接入 WinRT BLE GATT 0x2A19 扫描；实测 QCY-T18 无标准电池服务，T13/BT04-E 连接超时；如实显示未知 |
| 5 | 后台 BLE 扫描阻塞 UI | ✅ 独立线程池扫描 + 30 秒缓存；主流程只读缓存；实测 App 连续运行 28 秒稳定 |

- `HID++ 1.0` 探测：GET 0x81 reg 0x00/0x07/0x0D 对设备 1/2 均返回 `8F-81-...-01`（invalid subID），设备 3 返回 0x08；确认该接收器不提供 1.0 寄存器电量。

- 稳定性：2 秒轮询 + 后台 BLE 扫描，App 连续运行 28 秒未退出。

### 四、遗留

- 鼠标 `Wireless Mouse` 无电量上报是设备/接收器协议限制，软件无法凭空读取；若用户提供具体型号，可再尝试该型号的私有协议。

- 私有 2.4G 协议仍未自动逆向；`IBatteryProvider` 作为扩展点。
- 同型号双接收器仍按 `VID:PID` 合并；副屏/竖向任务栏不显示面板。

### 五、结论

- 刷新慢、拔插残留已修复；鼠标与蓝牙都增加了明确的“为何没有电量”说明，并接入标准 BLE GATT 真实读取路径。

## 第 5 轮 · 拔插清除与 1 秒刷新

> 流程：主智能体定位 + 真机验证（定向修复）
> 日期：2026-10-23 · 反馈：拔掉设备后仍一直显示；刷新率再提高

### 一、根因

1. **WM_DEVICECHANGE 没有真正订阅**：`DeviceChangeWindow` 只是一个普通 `NativeWindow`，没有调用 `RegisterDeviceNotification`。HID 设备接口的到达/移除通知不会送到该窗口，插拔只能等轮询，且部分场景完全不触发。
2. **合并逻辑过于宽容**：接收器仍插着、但无线设备关闭/拔掉时，HID 枚举仍会看到接收器的鼠标/键盘集合，生成“已连接但无电量”的占位条目。`MergeSnapshots` 看到同前缀/同类别的占位条目，就继续保留旧的 30% 电量，导致永久残留。
3. **启动缓存**：旧缓存键为 `cache`，只要系统里还有任意同类设备，缓存就可能被保留，进一步加重残留。

### 二、修复

- `DeviceChangeWindow` 调用 `RegisterDeviceNotification`，按 HID 设备接口类 GUID 注册；`DestroyHandle` 中 `UnregisterDeviceNotification`。实测返回的设备通知句柄非 0。
- 轮询从 2 秒改为 **1 秒**；HID++ 特性/电量/名称查询超时降为索引 1–2 200ms、3–6 120ms。整轮 `ReadAll` 实测 **1.468 秒**。
- `ApplySnapshot` 改为**以最新枚举结果为准**（`_snapshot = fresh`），不再用旧快照补位。设备/接收器消失、无线设备关闭后不再保留旧电量；接收器仍在但设备无电量时显示空/虚线电池，而不是上次的 30%。
- 移除 `MergeSnapshots`/`KeyPrefix`/`_failedPolls` 的旧值保留逻辑；保留启动时的短缓存，仅用于首轮读取前，首轮结果到达后立即覆盖。
- 1 秒轮询 + 设备通知 + pending 刷新：插拔事件立即触发；若正在读取，本次结束后立刻补刷。

### 三、验证

- `_notification` 句柄非 0，说明 HID 设备通知注册成功。
- `ReadAll` 1.468 秒（接收器在、设备休眠时），满足 1 秒轮询下的及时更新。
- 当前枚举：鼠标/键盘无电量（设备休眠或鼠标不支持上报）、QCY-T13 未知、罗技接收器无支持项；面板不会显示幽灵电量。
- 真机拔插由用户复测；代码路径为：WM_DEVICECHANGE → `RefreshNow` → 1 秒内重新枚举 → 新快照覆盖。

### 四、取舍与遗留

- 设备休眠时不再保留上次电量；面板显示空/虚线电池。这是为了彻底避免“拔掉后一直显示”的残留。若希望休眠时仍显示上次值，可另加“仅休眠保留、拔插立即清除”的设备级状态判断，但需要区分休眠与拔掉，当前选择更可靠。
- 鼠标 `Wireless Mouse` 无 HID++ 电量通道（2.0 特性表/1.0 寄存器均不可用）；QCY 耳机无标准 BLE 0x2A19。硬件限制不变。
- 同型号双接收器仍按 `VID:PID` 合并；副屏/竖向任务栏不支持。

### 五、结论

- 拔插不消失的根因已修复：设备通知已注册，快照不再保留旧电量，轮询 1 秒。
- 代价是休眠时不再显示上次值，但不会再出现拔掉后的幽灵电量。
- 本地提交，未推送。

## 第 6 轮 · 轮询卡死恢复

> 流程：主智能体定位 + 运行日志验证（定向修复）
> 日期：2026-10-23 · 反馈：无论拔接收器还是关键盘，显示完全不变

### 一、根因

- 只有一个 `BatteryTray.exe` 实例，不是旧进程叠加。
- 拔插发生在 HID 读取过程中时，`HidConnection` 的取消路径可能在 `CancelIo` 后无限等待 `GetOverlappedResult(..., true)` 完成；后台轮询线程永远不返回，`_polling` 一直为 1，后续刷新全部被丢弃，面板停在旧快照。
- 这正好表现为：拔接收器、关键盘后四类图标/电量完全不变，进程仍然存在且响应。

### 二、修复

- 新增 **1 秒轮询看门狗**：如果 `_polling` 已持续超过 3 秒，废弃当前代际（`_pollGeneration++`），强制复位 `_polling`，并启动新的后台读取线程。卡死线程被放弃，新线程重新枚举 HID；面板在 3–4 秒内恢复更新。
- 读取结果携带代际号；被看门狗废弃的旧线程即使之后返回，也不会覆盖新快照。
- 正常轮询不递增代际，避免 1 秒定时器把刚完成的快照误判为过期。
- 新增快照日志（`%TEMP%\BatteryTray.snapshot.log`）：仅在设备列表/支持状态/百分比变化时追加一行，包含 `Key/Category/Connection/Supported/Percent`，用于确认枚举结果是否真的变化。
- 保留 1 秒轮询、HID 设备通知、以最新快照为准的清除逻辑。

### 三、验证

启动后日志：

```text
13:31:35 count=4 supported=False [鼠标/键盘/耳机/接收器占位]
13:31:37 count=3 supported=True  [键盘 30%, 鼠标无电量, 耳机蓝牙]
```

- 两次快照在 2 秒内变化，说明轮询/UI 更新链路正常。
- 进程 `Responding=True`；看门狗已编译进当前 exe。
- 拔接收器后，日志应出现只含蓝牙耳机的快照；只关键盘时，接收器仍会枚举键盘集合，图标可能保留但电量会变成空电池。

### 四、取舍与遗留

- 看门狗会放弃卡死的旧线程；该线程及其 HID 句柄可能泄漏直到进程退出。正常情况不会触发，只有驱动取消不返回时才会。
- 仅关闭键盘时，接收器仍暴露键盘 HID 集合，因此四类面板可能仍显示键盘图标（电量清空）。要让图标也消失，需要读取 HID++ 设备在线状态（0x1D4B 等），当前鼠标/键盘不支持可靠返回。
- 鼠标 `Wireless Mouse` 无电量通道；QCY 耳机无标准 BLE 0x2A19，硬件限制不变。

### 五、结论

- 轮询卡死导致的“拔了不变”已通过看门狗恢复；日志可证明快照确实在变化。
- 若用户再次复现，直接查看 `%TEMP%\BatteryTray.snapshot.log`：若拔接收器后日志条目不变，则是枚举问题；若日志变空而面板不变，则是渲染问题。
- 本地提交，未推送。

## 第 7 轮 · 分层位图刷新

> 流程：主智能体回读源码 + 真机截图验证
> 日期：2026-10-23 · 反馈：托盘图标能实时变化，但时钟上方面板跟不上，必须点开“显示隐藏图标”才刷新

### 一、根因

- `DevicePanelForm.SetDevices` 会设置 `_dirty=true`，`Reposition` 里调用 `RenderSurface()` 把新内容画到 `_surface` 位图。
- 但把位图推到屏幕的 `UpdateLayeredWindow` 只在 `!Visible || moved` 时调用。面板已经可见且位置没变时，新位图虽然画好了，却从未上传到分层窗口。
- 点开“显示隐藏图标”会让面板 `Hide()`；弹层关闭后 `Visible=false`，`Reposition` 走到 `!Visible` 分支，才调用 `UpdateLayeredWindow` 并 `Show()`，于是画面终于刷新。这正是“点一下隐藏图标才跟上”的原因。
- 数据层和托盘图标一直正常，只有分层窗口的上传路径漏了脏标记。

### 二、修复

- `Reposition` 增加 `needsUpdate`：只要本次执行了 `RenderSurface()`（`_dirty` 为真），无论位置是否变化、是否可见，都调用 `UpdateLayered(x, y)`。
- 条件改为 `if (needsUpdate || !Visible || moved)`。
- 弹层打开时仍会 `Hide()`，`_dirty` 保留；弹层关闭后重新渲染并上传，避免旧画面。
- 1 秒轮询、看门狗、以最新快照为准的清除逻辑不变。

### 三、验证

- 启动 1.2 秒截图：耳机槽只有图标，没有蓝牙符号。
- 5 秒后、**未点击“显示隐藏图标”**截图：耳机槽自动出现蓝牙符号，键盘电量填充更新。
- 快照日志同时显示：

- 只关闭键盘时接收器仍暴露键盘 HID 集合，键盘图标可能保留、电量清空；这是接收器行为，不是刷新问题。
- 鼠标无 HID++ 电量通道、QCY 无标准 BLE 0x2A19，硬件限制不变。

### 五、结论

- “面板跟不上、点隐藏图标才刷新”的分层窗口上传缺陷已修复，真机截图验证通过。

## 第 8 轮 · 罗技键盘粗粒度电量

> 流程：主智能体真机探测 + 源码修正
> 日期：2026-10-23 · 反馈：键盘装两组 5 号电池（1.3V 与 1.6V）都显示 30%

### 一、真机探测结果

对键盘（HID++ 设备 1，名称 `Wireless Keyboard`）逐项探测：

| 特性 | 结果 |
|------|------|
| 0x1001 Battery Voltage | **不支持**（GetFeature 返回 -1） |
| 0x1004 Unified Battery | 支持，但 capabilities 的 state-of-charge 标志为 0，status 也是 0；**没有百分比** |
| 0x1000 Battery Status | 支持；响应 `1E 05 00`：原始值 30%，档位代码 5 |
| 0x0005 Device Name | `Wireless Keyboard`，类型键盘 |
| 0x1D4B Wireless Status | 有特性索引，但 function 0/1 无响应 |

结论：这块键盘固件只上报**粗粒度档位**（临界/低/良好/满）和一个人为的 30% 原始值，不提供电压。1.3V 与 1.6V 电池都落在“良好”档，所以原始值仍是 30；不是缓存、不是读取失败。

### 二、代码修正

- 修正 0x1000 响应的字段解释：原代码把 `response[5]` 误写成“下一档 5%”，它实际是**档位代码**（5=良好）；`response[6]` 也不是状态。现在：
  - `Detail = "HID++ 0x1000 电池状态：设备档位 良好（档位代码 5，粗粒度；设备原始值 30%）"`
  - 工具提示追加“（粗）”，提醒不是精确电压百分比。
  - 状态窗口新增说明：“部分罗技键盘只上报粗粒度档位（临界/低/良好/满），不支持电压百分比；更换 1.3V/1.6V 电池后可能仍显示同一档。”
- 未修改百分比值本身：设备上报 30%，不能凭空改成电压结果。

### 三、为什么不能修成随电压变化

- 0x1001 电压特性不存在；0x1004 没有 state-of-charge；HID++ 1.0 的 0x07/0x0D 寄存器之前也已实测返回错误 0x01。
- 没有电压数据就无法计算 1.3V/1.6V 对应的百分比；任何“变化”都只能是猜测。
- 该键盘为 2×AA 设计，1.6V 锂电池可能不在其电压检测范围内；建议用 1.5V 碱性电池、断电 10 秒后重新开机/重新配对，再观察设备本身是否更新档位。可在 Logitech SetPoint/Options 中对照，若那边也显示 30%，即为固件/硬件限制。

### 四、可选改进

- 如果用户不希望看到误导性的 30%，可把键盘槽改为**粗粒度显示**：满/良好/低/临界，仪表按档位着色，状态页保留原始 30%。这更符合设备的真实能力，但仍无法区分 1.3V 与 1.6V。
- 若后续换用支持 0x1001 电压的罗技设备，可增加电压→百分比换算。

### 五、结论

- 修正了档位字段误解和不准确的“下一档 5%”文案，明确标注粗粒度。
- 30% 恒定是键盘固件只提供粗粒度档位所致，软件无法从该设备读取实际电压；已如实说明，不再伪装成精确百分比。
- 本地提交，未推送。
